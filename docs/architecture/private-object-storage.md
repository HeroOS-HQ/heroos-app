# HeroOS Private Object Storage

**Status:** Storage primitive implemented (M1-07) and proven locally. Production S3 adapter deferred to M5 (cloud activation; [Delivery Plan](../milestones/delivery-plan.md))\
**Owner:** Technical Lead\
**Milestone:** M1 — Foundation & Security\
**Issue:** M1-07 — Establish secure storage, secrets, logging & backup foundation\
**Related:** [ADR-005](../decisions/ADR-005-document-storage.md),
[Tenant Isolation](tenant-isolation.md), [Production Security Gates](production-security-gates.md)

## 1. Summary

M1-07 provides a **secure storage primitive**, not the HeroOS Document domain.
It stores and returns private bytes for exactly one authorized Company. Document
metadata, types, statuses, workflows, retention and attachments are M2 work
(ADR-005). They will build on this primitive.

```text
Verified credential -> HeroOS User -> Membership      (M1-05)
        ↓
AuthenticatedCompanyContext
        ↓
CompanyScope                                          (M1-06, trusted Company)
        ↓
PrivateObjectService                                  app/storage/service.py
        ↓
StorageKey  companies/<company uuid>/<object uuid>    server-generated
        ↓
PrivateObjectStorage provider                         app/storage/base.py
        ↓
local filesystem (development)  |  private S3 (M5)
```

There is no database table for objects in M1-07. Company scoping comes from the
key namespace, so no tenant-private table was needed. When M2 adds document
metadata, that table must follow the
[tenant-isolation contract](tenant-isolation.md#9-contract-for-future-private-entities-m2-and-later)
(`company_id`, RLS, scoped repository, runtime grants, cross-tenant tests).

## 2. Keys and identifiers

`app/storage/keys.py`

- A key is `companies/<company uuid>/<object uuid>`. Nothing else can be a key.
- The Company UUID always comes from `scope.company_id`. It never comes from a
  request body, query, header, filename or the key itself.
- Object UUIDs are generated by HeroOS (`uuid4`) when an object is stored.
- `StorageKey` can only be built from two non-nil `UUID` instances, or parsed
  from the exact canonical string. Client-presented identifiers go through
  `parse_object_id`, which accepts only the canonical lowercase hyphenated UUID.
  These are rejected before any provider sees them: `../`, absolute paths,
  `C:\`, `%2e%2e%2f`, braces, `urn:uuid:`, upper case, whitespace, NUL and the
  nil UUID.
- Original filenames, if ever supported, are **metadata only**. They never become
  part of a key or a path.

## 3. Company-authorized access

`PrivateObjectService` (`store`, `read`, `exists`, `delete`) is the only
application entry point:

- every method takes a `CompanyScope`. Anything else, including a raw UUID or an
  `AuthenticatedCompanyContext`, is refused;
- no method accepts a Company, key, path or filename;
- `store` always creates a new object with a new server-generated UUID. Objects
  are **write-once**. There is no overwrite or update path, so another Company
  cannot overwrite an object even if it knows the UUID;
- `read`, `exists` and `delete` resolve the UUID inside the caller's own
  namespace. Another Company's object, a deleted object, a malformed identifier
  and a UUID that never existed all behave the same way (`ObjectNotFoundError` /
  `False`), so object existence in other Companies is never revealed.

Routes depend on `CompanyDb` and `ObjectStorage` (`app/storage/dependencies.py`).
No production object route exists in M1. Test-only routes prove the HTTP chain.

## 4. Development filesystem provider

`app/storage/local.py`. **Development only**: refused unless `HEROOS_ENV=development`
(in `Settings` and again in the provider constructor).

| Control | Behaviour |
| --- | --- |
| Root | `HEROOS_LOCAL_STORAGE_ROOT`, required and absolute. Refused if it is relative, a symlink, a file, not owned by the API user, inside the HeroOS source tree, or under a directory named `public`, `static`, `www`, `htdocs` or `wwwroot` |
| Permissions (POSIX) | root, `companies/` and each Company directory are `0700`. Objects are `0600`. Modes are set explicitly, not inherited from the umask, and broader existing modes are tightened |
| Containment | the key is re-parsed from its canonical string, so every path segment is the fixed prefix or a UUID. The parent directory must resolve inside the root, so a symlinked Company directory is refused. Objects are opened with `O_NOFOLLOW`, so a symlinked object is never followed |
| Atomic writes | data goes to a `0600` `mkstemp` file in the same directory, is `fsync`ed and is published with `os.link`, which is atomic and never replaces. Partial files are removed on failure |
| Deletes | `unlink`. A deleted object is gone from the provider |
| Errors | fixed messages (`StorageError`, `ObjectNotFoundError`, …), raised `from None`. Paths, keys and OS error text never leave the module |
| Web exposure | no static mount or file route exists (tested). The root is never inside a web-served directory or the repository. `.gitignore` adds a second guard |

On non-POSIX systems the permission steps are skipped. Containment, write-once
and fixed errors still apply.

## 5. Configuration

| Variable | Values | Rules |
| --- | --- | --- |
| `HEROOS_STORAGE_PROVIDER` | unset, `local`, `s3` | Unset: no storage, every object operation is refused (`StorageConfigurationError`), never a fallback. `local`: development only. `s3`: the M5 contract. The API **refuses to start** until the adapter exists. Other values are rejected |
| `HEROOS_LOCAL_STORAGE_ROOT` | absolute path | Required for `local`. Rejected with any other provider and in staging/production |

The provider is built at startup, so unsafe or unavailable storage
configuration stops the API instead of failing per request. There is no
hard-coded bucket, AWS account, credential or fake signed URL anywhere, and no
test contacts AWS.

## 6. Production S3 contract (M5)

**Not active. Nothing in AWS exists for this yet.** The M5 S3 adapter must
implement `PrivateObjectStorage` and satisfy all of the following:

- **Private bucket** per environment, with S3 Block Public Access enabled at the
  account and bucket level, no public ACLs or bucket policies, and Object
  Ownership "bucket owner enforced" (ACLs disabled).
- **Encryption at rest** (SSE-S3 or SSE-KMS; the KMS key choice is made at M5).
  **HTTPS only**: a bucket policy denies `aws:SecureTransport = false`.
- **Scoped IAM**: the API task role gets only `s3:GetObject`, `s3:PutObject` and
  `s3:DeleteObject` on `arn:aws:s3:::<bucket>/companies/*`, no `s3:ListBucket`
  beyond what the adapter needs, and no bucket administration.
- **Same keys**: `companies/<company uuid>/<object uuid>`. The provider receives
  only `StorageKey` values from `PrivateObjectService`.
- **Write-once**: `PutObject` with `If-None-Match: *` (or an equivalent
  conditional write), mapping a conflict to `ObjectExistsError`.
- **Controlled access** for downloads that bypass the API:

  ```text
  request -> HeroOS authentication -> Company authorization (Membership)
          -> object scope validation (key built from CompanyScope)
          -> short-lived pre-signed GET for that one key
          -> private object
  ```

  A pre-signed URL may be generated **only after** Company authorization, for one
  key, with a short expiry (the value is chosen at M5). Possession of a key or
  path is never authorization. The bucket stays private.
- **Errors**: AWS error messages, bucket names and keys are not returned to
  clients or logged verbatim. The provider raises the same fixed-message errors.
- **Versioning, lifecycle and retention**: not decided. These depend on
  PRIV-004, PRIV-018 and PRIV-019 in the
  [decision register](../privacy/decision-register.md).

| File | Proves |
| --- | --- |
| `tests/storage/test_storage_keys.py` | canonical layout and round trip; 21 unsafe object identifiers and 15 non-canonical keys rejected; nil and non-UUID values rejected |
| `tests/storage/test_local_storage.py` | put/get/exists/delete, write-once, deleted and missing objects, no partial files after a failed publish, `0700`/`0600` under umask 0, broad existing modes tightened, namespace separation, raw strings and tampered keys rejected before filesystem access, symlinked Company directory and symlinked object refused, errors without paths, root refusals (environment, web-served, source tree, relative, symlink, file) |
| `tests/storage/test_storage_settings.py` | local allowed in development only, root rules, unknown providers rejected, `s3` refused until an adapter exists, factory re-checks the environment |
| `tests/storage/test_company_object_access.py` | A/B read, exists and delete in both directions; a known foreign UUID behaves exactly like a missing object; no overwrite path; only `CompanyScope` accepted; unconfigured storage fails closed; no static or file routes; HTTP over the real bearer → Membership → `CompanyScope` chain (404 in own Company, 403 for the other Company, client `company_id` in query/header ignored, traversal references never resolve, 401 without a credential) |

Mutation checks (M1-07): removing the Company namespace, trusting raw key
strings, removing canonical re-parse and containment, and dropping
`O_NOFOLLOW`/explicit modes each made the suite fail.
